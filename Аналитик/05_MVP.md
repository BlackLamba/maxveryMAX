# 05. MVP проекта

## 1. Цель MVP

Цель MVP — проверить основную продуктовую гипотезу: **может ли сервис помочь пользователю быстрее выбрать подходящую городскую активность на основе его индивидуальных ограничений**.

MVP не должен решать задачу создания новой универсальной афиши.

Это особенно важно, поскольку существующая инфраструктура уже содержит значительный объём информации о культурных мероприятиях. Например, «Культура.РФ» предоставляет всероссийскую афишу, а PRO.Культура.РФ позволяет учреждениям размещать события на федеральных и региональных афишах. По данным PRO.Культура.РФ, сотрудники 22 000 учреждений культуры из 89 регионов размещают через платформу более 200 000 событий в год. [PRO.Культура.РФ](https://pro.culture.ru/?categories=obrazovatelnye-uchrezhdeniya&entityType=places&locales=193)

Следовательно, MVP должен проверять именно **механизм выбора и сопоставления**, а не наличие ещё одного каталога.

---

# 2. Пользовательский путь MVP

Основной путь пользователя:

```text
Задать ограничения
        ↓
Получить подходящие активности
        ↓
Сравнить варианты
        ↓
Выбрать активность
        ↓
Перейти к официальному источнику
```

### Пример

Пользователь вводит:

> Сегодня, с 18:00 до 21:00
> Интересуют выставки и концерты
> Бюджет — до 1500 ₽
> Желательно недалеко

Система возвращает несколько вариантов:

| Активность | Время | Стоимость | Расстояние | Почему подходит               |
| ---------- | ----: | --------: | ---------: | ----------------------------- |
| Выставка А | 18:30 |     500 ₽ |       2 км | Подходит по времени и бюджету |
| Концерт Б  | 19:00 |    1200 ₽ |       3 км | Подходит по интересам         |
| Лекция В   | 18:00 |       0 ₽ |     1,5 км | Бесплатно и находится рядом   |

Пользователь самостоятельно выбирает один из вариантов и переходит к официальному источнику.

# 3. Состав MVP

## 3.1. Must Have

Must Have — функции, без которых невозможно проверить основную гипотезу. Такой подход соответствует классической логике MoSCoW: Must — обязательные элементы, Should — важные, но не критичные, Could — желательные, Won't — сознательно исключённые из текущего этапа. [GOV.UK Service Manual — Deciding on priorities](https://www.gov.uk/service-manual/agile-delivery/deciding-on-priorities)

### Ввод параметров

Пользователь должен иметь возможность указать:

* дату;
* временной интервал;
* тип активности;
* интересы;
* максимальный бюджет;
* допустимое расстояние.

---

### Каталог активностей

Каждая активность должна содержать структурированные данные:

* название;
* категория;
* дата;
* время начала;
* место проведения;
* стоимость;
* описание;
* возрастное ограничение, если оно известно;
* ссылка на источник.

Для MVP допускается использование подготовленного набора данных.

Если данные не получаются через реальную интеграцию, они должны быть явно обозначены как **тестовые, подготовленные или синтетические**.

Нельзя представлять тестовый набор как данные реального времени.

---

### Фильтрация

Система должна исключать варианты, которые явно не соответствуют заданным ограничениям.

Например:

```text
Бюджет пользователя: до 1000 ₽

Мероприятие А: 700 ₽ → подходит
Мероприятие Б: 1500 ₽ → не подходит
```

---

### Ранжирование

После фильтрации система должна определить порядок отображения оставшихся вариантов.

На первом этапе можно использовать простую систему баллов:

```text
+ баллы за совпадение категории
+ баллы за совпадение интересов
+ баллы за соответствие времени
+ баллы за соответствие бюджету
+ баллы за близость
```

Конкретные веса параметров являются частью проектной гипотезы и могут изменяться после пользовательского тестирования.

Сложная ML-модель для первого MVP не обязательна.

---

### Карточка активности

Пользователь должен получить основную информацию без необходимости открывать несколько внешних страниц.

Минимальная карточка:

```text
Название
Категория
Дата и время
Место
Стоимость
Краткое описание
Почему подходит
Официальный источник
```

---

### Переход к официальному источнику

Для каждой активности должна присутствовать ссылка на источник, где пользователь может проверить актуальную информацию и совершить дальнейшее действие.

Это особенно важно для событий с ограниченным сроком актуальности.

Например, в документации PRO.Культура.РФ указано, что после модерации событие публикуется на «Культура.РФ» и других ресурсах. [PRO.Культура.РФ — документация](https://pro.culture.ru/documentation/online.pdf)

# 4. Should Have

Функции, которые существенно улучшают MVP, но не являются обязательными для проверки основной гипотезы:

* сортировка по расстоянию;
* сортировка по стоимости;
* сортировка по релевантности;
* карта;
* расчёт времени в пути;
* отображение бесплатных мероприятий;
* сохранение понравившихся вариантов;
* возможность изменить параметры поиска без повторного заполнения формы;
* отображение альтернативных вариантов.

---

# 5. Could Have

Функции, которые могут быть добавлены при наличии времени:

* ввод запроса естественным языком;
* рекомендации для нескольких пользователей;
* подбор активности для пары или группы;
* построение маршрута;
* история поисков;
* персонализация;
* уведомления;
* объяснение рекомендации;
* анализ отзывов.

---

# 6. Won't Have в MVP

Сознательно не включаем:

* собственную продажу билетов;
* собственную регистрацию на мероприятия;
* собственную платёжную систему;
* социальную сеть;
* отзывы пользователей;
* полноценную систему рейтингов;
* интеграцию со всеми билетными сервисами;
* интеграцию со всеми учреждениями культуры;
* автоматический сбор информации со всего интернета;
* полноценного AI-ассистента;
* сложную генеративную модель;
* построение многодневных маршрутов.

---

# 7. Источник данных

Для демонстрационного MVP возможны два режима.

### Режим A — подготовленный набор данных

Используется заранее сформированный набор активностей.

Преимущества:

* контролируемое качество данных;
* предсказуемая демонстрация;
* не требуется разрабатывать интеграции;
* проще проверить алгоритм подбора.

Недостаток — данные не являются гарантированно актуальными в реальном времени.

---

### Режим B — реальный источник

В качестве источника может использоваться существующая информационная система, если технические и правовые условия позволяют это сделать.

При этом необходимо явно фиксировать:

* источник данных;
* дату получения;
* доступные поля;
* частоту обновления;
* ограничения источника.

Наличие существующих платформ не означает автоматического наличия API или разрешения на произвольное использование данных.

---

# 8. Что демонстрируем на защите

Демонстрация MVP должна строиться вокруг одного понятного сценария.

### Шаг 1

Пользователь сообщает:

> «Сегодня вечером хочу куда-нибудь сходить».

### Шаг 2

Указывает:

* время;
* интересы;
* бюджет;
* расстояние.

### Шаг 3

Система показывает несколько подходящих вариантов.

### Шаг 4

Пользователь сравнивает их.

### Шаг 5

Система объясняет соответствие каждого варианта заданным условиям.

### Шаг 6

Пользователь открывает официальный источник выбранной активности.

Таким образом демонстрируется не просто каталог мероприятий, а **механизм перехода от неопределённого желания к конкретному варианту досуга**.

---

# 9. Критерии успешности MVP

MVP должен позволить измерить:

| Показатель                             | Что проверяет                                                 |
| -------------------------------------- | ------------------------------------------------------------- |
| Время выбора                           | Стало ли быстрее принять решение                              |
| Количество просмотренных вариантов     | Сократился ли объём ручного поиска                            |
| Количество переходов между источниками | Снизилась ли необходимость самостоятельно собирать информацию |
| Доля пользователей, выбравших вариант  | Удалось ли довести пользователя до решения                    |
| Оценка удобства                        | Понятен ли пользователю механизм подбора                      |
| Релевантность выбранных вариантов      | Соответствуют ли результаты ограничениям пользователя         |

Конкретные целевые значения показателей определяются после первого пользовательского тестирования.

---

# 10. Граница MVP

Главная граница MVP:

> **Мы не создаём новую афишу. Мы создаём механизм выбора подходящей активности из доступной информации.**

Поэтому MVP считается достаточным, если пользователь может:

**задать ограничения → получить несколько подходящих вариантов → понять различия между ними → выбрать вариант → перейти к официальному источнику.**

Всё, что не требуется для прохождения этого пути, может быть вынесено за пределы первой версии.
