# app/ — код проекта maxveryMAX

Эта папка — **корень кода**. Здесь лежат `docker-compose.yml`, `.env.example` и все модули продукта. Документация проекта (аналитика, архитектура, путь пользователя) лежит рядом, в соседних папках `docs/` и `Аналитик/` — код и документация не смешиваются.

Полное описание продукта, переменных окружения, портов, API-контракта и сценария проверки — в [корневом README](../README.md). Здесь — **карта папок: что зачем нужно и что в каждой папке должно находиться.**

## 1. Главное правило

```text
[Чат-бот]  [Мини-приложение]          ← интерфейсы для пользователя
      │             │
      └──────┬──────┘
             ▼
        backend/          ← только он общается с внешним миром по HTTP API
             │
             ▼
        PostgreSQL        ← единственный источник истины по событиям
             ▲
             │
         worker/          ← единственный, кто пишет события в БД
             ▲
             │
      mock_events.json / внешние провайдеры
```

**Инварианты, которые нельзя нарушать:**

1. **`worker/` пишет в БД, `backend/` читает из БД.** Никакой модуль больше не пишет события в базу.
2. **`bot/` и `miniapp/` ходят только в `backend/`** — не в БД, не к внешним афишам, не в `worker/`.
3. **Внешние источники данных не запрашиваются во время пользовательского запроса** — иначе недоступность чужого API ломает демо.
4. **`shared/` — только модели и справочники**, без бизнес-логики и без импортов из других папок.

## 2. Кто за что отвечает

| Папка | Владелец | Что это |
| --- | --- | --- |
| `bot/` | Антон | чат-бот MAX: диалог сбора параметров, deep link, уведомления |
| `backend/` | Женя | FastAPI: фильтры, ранжирование, карточка, избранное, аналитика кликов |
| `miniapp/` | Дима | мини-приложение: список, карточка, фильтры, состояния, адаптив |
| `worker/` | Олежа | загрузка и нормализация событий, тестовый набор, сиды |
| `shared/` | Общее | модели и enum категорий — изменения только по согласованию со всеми |
| `infra/` + корневые файлы | Общее (нужно закрепить) | Docker, compose, `.env.example`, README, сборка |

Изменение в чужой папке — через отметку в `Аналитик/09_task_list_и_распределение.md` и сообщение владельцу.

## 3. Дерево и назначение папок

```text
app/
├── backend/     # HTTP API для бота и мини-приложения (FastAPI) — читает PostgreSQL
├── bot/         # чат-бот в MAX — собирает параметры и открывает мини-приложение
├── worker/      # загрузка событий: провайдеры → нормализация → валидация → БД
├── miniapp/     # веб-интерфейс (Vite + React) — показывается внутри MAX
├── shared/      # общие модели и категории для Python и TypeScript
├── infra/       # Dockerfile'ы, nginx, скрипты БД и сборки
├── docker-compose.yml   # запуск всех сервисов одной командой
├── .env.example         # список переменных окружения без секретов
└── .gitignore           # .env, кэши, node_modules, dist и прочее
```

Коротко «зачем каждая папка»:

| Папка | Зачем нужна | Что было бы без неё |
| --- | --- | --- |
| `backend/` | единая точка доступа к данным для интерфейсов | фронт и бот тянули бы данные напрямую из БД и из чужих API |
| `bot/` | сбор ограничений пользователя там, где ему удобно — в чате | пользователь не смог бы начать сценарий без мини-приложения |
| `worker/` | подготовка и обновление каталога событий | данные пришлось бы вбивать руками и они бы устаревали |
| `miniapp/` | сравнение вариантов: список, карточки, фильтры | в чате невозможно нормально сравнить 5–10 карточек |
| `shared/` | один список категорий и одна модель события для всех | категории в боте, бэке и фронте разъехались бы |
| `infra/` | воспроизводимый запуск `docker compose up` | «у меня работает, у тебя нет» |

## 4. Файлы в корне `app/`

| Файл | Зачем | Кто ведёт |
| --- | --- | --- |
| `docker-compose.yml` | поднимает `postgres`, `backend`, `worker`, `bot`, `miniapp`; описывает порты, тома, healthcheck'и и зависимости | Общее |
| `.env.example` | **полный список переменных окружения с заглушками** — по нему любой человек настраивает проект. Реальные токены сюда не попадают никогда | Общее |
| `.gitignore` | `.env`, `__pycache__/`, `.venv/`, `node_modules/`, `dist/`, `.mypy_cache/`, `*.pyc`, дампы БД | Общее |
| `README.md` | этот файл: карта папок и требования к содержимому | Общее |
| `Makefile` *(опционально)* | короткие команды: `make up`, `make seed`, `make logs`, `make reset-db` | Общее |

Порядок работы с `.env`: скопировать `.env.example` → `.env`, заполнить секреты локально, `.env` **никогда** не коммитить и не пересылать в чат.

## 5. Подробно по каждой папке

### 5.1. `backend/` — API

**Зачем:** единственная точка, через которую бот и мини-приложение получают данные. Здесь живут фильтры, ранжирование с объяснением «почему подходит», карточка события, избранное и аналитика кликов.

**Что должно лежать:**

```text
backend/
├── app/
│   ├── main.py              # создание FastAPI, CORS, подключение роутеров, /api/health
│   ├── config.py            # чтение переменных окружения (pydantic-settings)
│   ├── db.py                # движок и сессия SQLAlchemy (async), базовый класс моделей
│   ├── models/              # ORM-таблицы: cities, categories, events, event_sources,
│   │                        #   tags, event_tags, providers, users, favorites,
│   │                        #   user_preferences, event_interactions
│   ├── schemas/             # Pydantic-схемы запросов и ответов API
│   ├── api/                 # роутеры по доменам: health, cities, categories, events,
│   │                        #   search, favorites, preferences, analytics
│   ├── services/            # бизнес-логика: фильтрация, ranking.py (баллы + reason),
│   │                        #   hint.py (подсказка при пустом результате), clicks.py
│   └── repositories/        # запросы к БД, изолированные от роутеров
├── migrations/              # Alembic: версии схемы БД
├── tests/                   # pytest: фильтры, ранжирование, формат ошибок
├── requirements.txt         # зависимости
└── Dockerfile
```

**Что должно быть готово:** `GET /api/health`, `/api/cities`, `/api/categories`, `GET /api/events` с фильтрами (`city_id`, `date_from`, `date_to`, `time_from`, `time_to`, `category`, `price_max`, `is_free`, `radius_km`, `sort`, `limit`), `GET /api/events/{id}` с `reason`, `POST /api/events/{id}/click`; единый формат ответа (`items`, `total`, `hint`) и единый формат ошибок.

**Что здесь НЕ должно находиться:** код загрузки событий из внешних источников (это `worker/`), обращения к Bot API MAX (это `bot/`), секреты в коде, сырые SQL-строки в роутерах.

**С кем связан:** читает `shared/models.py` и `shared/categories.py`; читает БД; его HTTP API используют `bot/` и `miniapp/`.

### 5.2. `bot/` — чат-бот MAX

**Зачем:** точка входа в продукт и канал уведомлений. Бот — «тонкий»: он только встречает пользователя приветствием и даёт кнопку открытия мини-приложения. Весь сбор параметров (город, даты, интересы, бюджет) и вся работа с каталогом происходят в мини-приложении — это решение зафиксировано в `docs/02_user_journey.md` и `Аналитик/06_MAX_и_UX.md` (причины: календарь, мультиселект интересов и возможность изменить любой фильтр без повторного прохождения диалога).

**Что должно лежать:**

```text
bot/
├── main.py            # точка входа: инициализация Bot API, long polling, запуск цикла уведомлений
├── config.py          # чтение env: MAX_BOT_TOKEN, BOT_NAME, BACKEND_URL, MINIAPP_BASE_URL,
│                      #   NOTIFICATIONS_POLL_INTERVAL_SECONDS, LOG_LEVEL
├── handlers.py        # /start (приветствие + open_app-кнопка), /help, бот-событие BotStarted,
│                      #   фоллбэк на любые другие сообщения
├── api_client.py      # асинхронный HTTP-клиент к backend/ (health, /api/notifications/*)
├── texts.py           # все пользовательские тексты в одном месте
├── notifications.py   # (Could Have, после базового сценария) фоновый опрос
│                      #   GET /api/notifications/pending → рассылка → POST .../ack
├── __main__.py        # запуск через python -m bot
├── requirements.txt   # зависимости: maxapi (оф. SDK MAX Bot API), httpx
└── Dockerfile         # в стиле остальных модулей, python:3.12-slim
```

**Что должно быть готово:**
- `/start` (и событие «пользователь нажал „Начать“» в профиле бота) отвечает приветствием и одной `open_app`-кнопкой «🎟 Открыть подборку», которая открывает привязанное к боту мини-приложение внутри MAX. Пейлоад фильтров не передаётся — они собираются уже в самом мини-аппе.
- `/help` — короткая инструкция.
- Любой другой текст не ломает бота: отвечается подсказкой с той же кнопкой открытия мини-аппа.
- Фоновый цикл уведомлений (Could Have): раз в `NOTIFICATIONS_POLL_INTERVAL_SECONDS` опрашивает backend, рассылает напоминания/обновления по избранным событиям, подтверждает отправку, корректно обрабатывает случай «пользователь заблокировал бота» (логирует и идёт дальше, не роняя цикл). Если эндпоинты `/api/notifications/*` ещё не готовы на бэке — цикл просто ждёт, не мешая работе бота.

**Что здесь НЕ должно находиться:** прямые запросы к PostgreSQL, обращения к внешним афишам, логика фильтрации/ранжирования, state machine с пошаговым сбором параметров (это устаревшая версия, противоречащая актуальному user journey), длинные тексты, зашитые в хендлеры.

**С кем связан:** ходит ТОЛЬКО в `backend/` (по инварианту из раздела 1); открывает мини-приложение через `OpenAppButton` (web_app = имя бота, URL мини-аппа настроен на платформе MAX для партнёров). Мини-апп получает контекст пользователя (initData) автоматически через MAX Bridge, боту не нужно отдельно передавать identity в deep link.

### 5.3. `worker/` — загрузка событий

**Зачем:** превращает внешние или тестовые данные в чистый каталог в БД. Именно воркер наполняет базу, из которой потом читает бэкенд.

**Что должно лежать:**

```text
worker/
├── __main__.py        # CLI: import / seed / scheduler
├── config.py          # путь к данным, интервал, ретраи, порог дедупликации
├── data/
│   └── mock_events.json   # 30–50 событий, поля модели Event (обязательно помечены как тестовые)
├── providers/
│   ├── base.py        # интерфейс EventProvider: fetch() → список сырых событий
│   ├── mock.py        # читает mock_events.json
│   └── kudago.py / timepad.py   # P1, после рабочего сквозного сценария
├── pipeline/
│   ├── normalize.py   # сырые данные → модель Event
│   ├── validate.py    # проверка обязательных полей, лог отбракованных записей
│   └── deduplicate.py # P1: rapidfuzz по title + дата + адрес
├── repository.py      # upsert в events, event_sources, tags, event_tags, providers
├── quality_score.py   # P1: простая формула полноты и качества записи
├── scheduler.py       # периодический запуск с интервалом
├── seed.py            # наполнение БД одной командой (города, категории, события)
├── tests/             # pytest: нормализация, валидация, идемпотентность импорта
├── requirements.txt
└── Dockerfile
```

**Что должно быть готово в первую очередь:** `python -m worker import --file data/mock_events.json` — рабочий импорт, идемпотентный по ключу `(source, source_id)`; `python -m worker seed`; обновление тестового набора с датами относительно текущей даты.

**Что здесь НЕ должно находиться:** HTTP-эндпоинты (это `backend/`), логика отображения, токены внешних сервисов в коде.

**С кем связан:** читает `shared/models.py`, `shared/categories.py`; пишет в PostgreSQL; его данные потребляет `backend/`.

### 5.4. `miniapp/` — мини-приложение MAX

**Зачем:** основное место выбора: список карточек, сравнение, фильтры без возврата в бот, карточка события со ссылкой на официальный источник и избранное. Открывается внутри MAX по deep link от бота.

**Что должно лежать:**

```text
miniapp/
├── index.html
├── package.json / package-lock.json
├── vite.config.ts        # dev-прокси /api → backend, настройки сборки
├── tsconfig.json
├── src/
│   ├── main.tsx          # точка входа: <MaxUI> + HashRouter
│   ├── App.tsx           # маршруты: список, карточка, избранное, фильтры
│   ├── api/              # клиент к backend/ (базовый путь /api), обработка ошибок
│   ├── pages/            # EventsList, EventDetails, Favorites, Filters
│   ├── components/       # EventCard, FilterBar, SortBar, Skeletons,
│   │                     #   EmptyState, ErrorState, Loader, ResultBanner
│   ├── hooks/            # useEvents, useFilters, useFavorites
│   ├── types/            # типы, синхронизированные со shared/models.py
│   ├── utils/
│   │   ├── launchParams.ts  # разбор start_param из window.WebApp + запасной ?query= для браузера
│   │   ├── format.ts        # форматирование дат, цен, расстояний
│   │   └── platform.ts      # MAX Bridge: platform, deviceName, initData
│   └── styles/           # глобальные стили и токены
├── public/               # статика: иконки, изображения-заглушки
├── Dockerfile            # сборка + раздача через nginx
└── nginx.conf            # статика + прокси /api → backend:8000
```

**Что должно быть готово:** экран списка, карточка события, фильтры и сортировки, избранное, обязательные состояния (Loader, EmptyState с подсказкой, ErrorState, скелетоны, баннер о результате действия), адаптив 360/375/390/414/430 px.

**Что здесь НЕ должно находиться:** обращения к внешним афишам, доступ к БД, свой backend, захардкоженные `http://localhost` (в браузере пользователя это не сработает — только относительный `/api`).

**С кем связан:** использует `shared/categories.ts`; ходит только в `backend/`; читает параметры запуска из MAX Bridge; открывается по ссылке от `bot/`.

### 5.5. `shared/` — общие модели и справочники

**Зачем:** один источник правды для тех сущностей, которые нужны сразу нескольким модулям. Если поменялся список категорий — он меняется здесь один раз, а не тремя правками в трёх папках.

**Что должно лежать:**

```text
shared/
├── models.py        # Pydantic-модели: Event, City, Category, FilterParams
├── categories.py    # enum категорий для Python (бот, бэкенд, воркер)
├── categories.ts    # тот же enum для TypeScript (мини-приложение)
└── __init__.py
```

**Что здесь НЕ должно находиться:** бизнес-логика, запросы к БД, работа с HTTP, тексты сообщений, что-либо зависящее от FastAPI или от React.

**Правила:** значения категорий в Python и TypeScript обязаны совпадать один в один; добавляя категорию, правим оба файла в одном коммите и сообщаем Антону и Диме; в модулях всегда `import shared...`, а не копия модели «у себя».

---

### 5.6. `infra/` — Docker и серверные конфиги

**Зачем:** всё, что делает запуск воспроизводимым: одна команда — и проект поднимается у любого человека на чистой машине.

**Что должно лежать:**

```text
infra/
├── nginx.conf            # отдача мини-приложения и прокси /api на backend
├── postgres/init.sql     # базовые справочники: города, категории (опционально)
├── Dockerfile.*          # если Dockerfile'ы удобнее держать здесь, а не в модулях
├── .dockerignore         # не тащить в образы .git, node_modules, .env, тестовые дампы
├── scripts/
│   ├── seed.sh           # импорт тестового набора после старта
│   └── wait-for-db.sh    # ожидание готовности PostgreSQL перед миграциями
└── README.md             # (опционально) заметки по инфраструктуре
```

**Что должно быть готово:** `docker compose up --build` поднимает `postgres + backend + worker + bot + miniapp`, сборка укладывается в 5 минут, `docker compose down -v` даёт чистый прогон.

**Что здесь НЕ должно находиться:** секреты, токены, пароли (только через `.env`), образы с зашитыми данными конкретного разработчика.

**Технический нюанс:** образы собираются из корня `app/`, потому что каждому модулю нужен общий код из `shared/`. Поэтому в Dockerfile путь до общих файлов указывается от корня: `COPY shared/ ./shared/`, а сборка запускается из корня (`docker compose build`).

## 6. Правила зависимостей между папками

| Кто | Может импортировать/использовать | Запрещено |
| --- | --- | --- |
| `backend/` | `shared/`, PostgreSQL | `bot/`, `worker/`, `miniapp/`, внешние провайдеры |
| `bot/` | `shared/`, HTTP API `backend/` | БД напрямую, `worker/`, внешние афиши |
| `miniapp/` | `shared/categories.ts`, HTTP API `backend/` | БД, `bot/`, `worker/`, внешние API |
| `worker/` | `shared/`, PostgreSQL, внешние провайдеры | HTTP-эндпоинты, `bot/`, `miniapp/` |
| `shared/` | ничего из папок проекта | любые импорты из `backend/`, `bot/`, `worker/`, `miniapp/` |
| `infra/` | — (только конфиги и скрипты) | код продукта |

Проверка перед коммитом: `grep -r "from backend" bot/ worker/ miniapp/` и `grep -r "import worker" backend/` должны быть пустыми.

## 9. Конвенции

* **Именование:** Python — `snake_case` для файлов и функций, `PascalCase` для классов; TS/React — `PascalCase` для компонентов, `camelCase` для остального.
* **Конфиг:** все переменные окружения читаются в `config.py` / `config.ts`, а не по коду через `process.env` и `os.environ`.
* **Тексты:** пользовательские тексты бота — в `bot/texts.py`; тексты интерфейса мини-приложения — отдельными константами, не разбросаны по компонентам.
* **Ошибки:** не глотать исключения молча — логировать и отдавать понятный ответ; в интерфейсе показывать ErrorState, а не пустой экран.
* **Данные:** всё тестовое помечается как тестовое (`data_origin='mock'`, бейдж «Демо-данные» в мини-приложении). Выдавать подготовленный набор за реальное время нельзя.
* **Git:** одна задача — одна ветка (`feature/...`), изменения в чужой папке — только с уведомлением владельца. Ветки и порядок работ — в `docs/03_roles_and_order.md`.
* **Поддержка этого файла:** появилась новая папка, файл или договорённость — сразу дописываем сюда, чтобы README не отставал от кода.
