# 04. Советы по тому, что делать

## 1. Делать в первую очередь

### 1.1. Зафиксировать один основной сценарий

Не строить «платформу всего досуга». Сначала:

> **найти подходящее мероприятие → посмотреть детали → купить / сохранить.**

### 1.2. Сделать Mini App основным UI

Каталог, фильтры и карточки естественнее работают в интерфейсе Mini App. Бот оставить для входа и коммуникации.

### 1.3. Получать данные заранее

Данные загружаются worker'ом и лежат в PostgreSQL.

Не ждать внешний API в пользовательском запросе без необходимости.

### 1.4. Сразу определить нормальную Event Model

Если Event Model плохая, дальше начнут ломаться:
- поиск;
- фильтры;
- карты;
- рекомендации;
- дедупликация.

### 1.5. Сразу сделать OpenAPI

Frontend и backend должны развиваться параллельно.

### 1.6. Сначала rule-based ranking, потом ML

Быстро добиться рабочего результата, затем улучшить ranking.

### 1.7. Сделать NLP как главную AI-демо-фичу

Лучший кандидат:

> «Хочу рок-концерт в Москве в субботу до 3000 рублей»

→ структура запроса → реальные мероприятия.

Это проще надёжно показать на демо, чем полноценную обученную систему рекомендаций.

### 1.8. Обязательно сделать fallback

При отказе KudaGo/Timepad пользователь должен продолжать видеть уже загруженные события.

### 1.9. Добавить аналитику с первого дня

Нужны хотя бы:
- открытие;
- поиск;
- просмотр события;
- избранное;
- переход к покупке.

### 1.10. Держать MVP маленьким

Победить можно не количеством функций, а цельностью сценария.

## 3. Как организовать Docker

Стартовый состав:

```text
backend
worker
frontend
postgres
```

Redis — только когда появляется конкретная задача:
- cache;
- rate limiting;
- очередь;
- быстрые ephemeral данные.

## 4. Как организовать документацию

Рекомендуемая папка:

```text
docs/
├── architecture.md
├── user-journey.md
├── api.md
├── event-model.md
├── decisions.md
└── demo.md
```

`decisions.md` должен фиксировать спорные решения:
- Mini App + Bot;
- modular monolith;
- PostgreSQL-first;
- внешние API через adapters;
- NLP как P0 AI-feature.

## 7. Полезные технические акценты

### Provider Adapter

Позволяет добавить новый источник без изменений frontend.

### Quality Score

Плохие или неполные события можно понижать в выдаче.

### Deduplication

Снижает повторения из разных источников.

### Deep Links

Позволяют открыть конкретное мероприятие через Bot.

### Cache / local DB

Снижает зависимость от внешних API.

## 8. Принцип разработки

Каждая функция должна отвечать на вопрос:

> **Станет ли пользователю быстрее понять, куда ему сходить?**

Если нет — это кандидат на P2.
