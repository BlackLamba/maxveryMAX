# 05. Советы по тому, чего не делать

## 1. Не делать микросервисы ради микросервисов

Не создавать десяток сервисов только потому, что «так масштабируемо».

Для хакатона это добавляет:
- Docker;
- networking;
- deployment;
- observability;
- точки отказа;
- время на отладку.

Использовать модульный монолит.

## 2. Не обращаться к KudaGo/Timepad напрямую из frontend

Нельзя строить:

```text
Mini App → KudaGo
Mini App → Timepad
```

Нужно:

```text
Mini App → Backend → Provider Adapters → Sources
```

## 3. Не строить продукт только как чат-бот

Чат хорош для уведомлений и естественного языка, но хуже для:
- сравнения карточек;
- фильтров;
- визуального каталога;
- выбора из многих вариантов.

Основной каталог — Mini App.

## 4. Не делать геолокацию обязательной

Не заставлять пользователя выдавать координаты при первом запуске.

Сначала выбор города.

Геолокация только для:
- «рядом со мной»;
- сортировки по расстоянию;
- карты.

## 5. Не строить полноценную карту первой фичей

Карта полезна, но не является ядром ценности.

Сначала:

```text
город → поиск → событие → покупка
```

Потом карта.

## 6. Не делать сложную ML-модель до появления рабочего поиска

Нельзя начинать с:
- deep learning recommender;
- сложного collaborative filtering;
- собственного foundation model;
- тяжёлого inference stack.

Сначала простые правила и реальные данные.

## 7. Не позволять AI генерировать события

AI не должен «придумывать» мероприятия.

Источник истины:

```text
KudaGo
Timepad
и другие валидные источники
```

AI только:
- понимает запрос;
- ранжирует;
- группирует;
- ищет семантически похожие реальные события.

## 8. Не тянуть внешний API в критический момент demo

Нельзя делать так, чтобы кнопка «Москва» зависела от доступности внешнего сервиса прямо сейчас.

Заранее наполнить локальный каталог.

## 9. Не пытаться покрыть весь кейс одновременно

Не нужно одновременно запускать:
- концерты;
- театр;
- спорт;
- туризм;
- волонтёрство;
- экскурсии;
- маршруты;
- социальную механику.

Архитектура может быть общей, MVP — узким.

## 10. Не делать встроенную покупку билета обязательным условием MVP

Если поставщик даёт ссылку на покупку, этого достаточно для первого результата.

Полноценный checkout внутри приложения — отдельная задача.

## 11. Не переусложнять DevOps

Не нужны:
- Kubernetes;
- service mesh;
- Kafka без реальной причины;
- отдельный API Gateway;
- десяток контейнеров;
- сложная observability-платформа.

Для MVP достаточно простого docker-compose/CI/CD и логирования.

## 12. Не делать «спам-рассылку» по умолчанию

Уведомления должны быть управляемыми:
- интересы;
- город;
- бюджет;
- частота;
- уровень релевантности.

Главная цель — полезное уведомление, а не максимальное количество отправок.

## 13. Не откладывать error states и fallback до последнего

Нужно заранее продумать:
- нет событий;
- API недоступен;
- событие устарело;
- не указана цена;
- нет изображения;
- пользователь не дал геолокацию.

## 14. Не тратить время на идеальный дизайн до проверки сценария

Сначала добиться:

```text
открыть → найти → выбрать → купить
```

Потом улучшать визуал.

## 15. Не использовать архитектуру как самоцель

На защите важно объяснить:

> Мы выбрали модульный монолит не потому, что микросервисы плохи, а потому что для хакатона он снижает операционную сложность и при этом сохраняет модульные границы.

## 16. Не строить слишком много фич до demo freeze

За несколько часов до защиты нужно заморозить новые функции и заниматься:
- тестированием;
- данными;
- fallback;
- стабильностью;
- demo script.
